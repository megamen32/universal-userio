### Existing RPC surfaces

**ExManager**: native, already authorized UserIO MCP; tools are *exactly*
`userio.messenger.question.{acquire,renew,pause,handoff,resume,result_saved,reconcile,complete,audit}`.
Each tool requires the exact existing authenticated principal (current owner/account grants, send capability); never supply `worker_id`, `holder`, `tenant`, account IDs or a replacement token. No read-only or revoked account upgrade. The wire uses `revision`, **not** `source_revision`; `reconcile`, **not** `reconcile_delivery`. **Effective principal compatibility gate:** UserIO maps `principal.service_account=True` to `dot` (requiring a verified dot binding), while `manager` requires the existing authenticated non-service `owner` principal with current account rights and `read_only=False`. ExManager's shared `userio` Airlock resource uses a saved MCP bearer credential whose *effective UserIO principal type must be verified*; a shared service token cannot be relabeled as manager by passing `holder` or using the Airlock owner ID. If the current registered credential resolves to service_account or read-only, fail closed and coordinate normal authorization; do not mint/borrow a token, widen scopes, or bypass the existing member binding. All successful MCP replies are **wrapped**:
```json
{"ok":true,"question":{"question_id":"<server-id>","holder":"manager","epoch":1,"lease_token":"<opaque-leased-token>","state":"active","result_ref":null,"lease_expires_at":1234.5}}
```
The example placeholders are not real IDs/tokens. Errors are `{"ok":false,"error":"<machine-reason>"}`; do not treat a partial response as an acquired lease. `acquire` inputs: `event_seq` (positive integer), `revision` (current source `edited_at` as string, `"0"` for unedited), `request_id` (stable idempotency ID); optional `ttl` 30–900s, `pending_question`, `card_id`. `renew` adds `lease_token,epoch`; `pause` requires `event_seq,revision,request_id`; `handoff` adds `target_holder="dot"|"manager"`; `resume` requires `event_seq,revision,request_id` (do not reuse old lease); `result_saved` adds current `lease_token,epoch,request_id,result_ref`; `reconcile` only `event_seq,revision,request_id`; `complete` adds current lease token/epoch; `audit` only `event_seq`.

**dot**: existing UserIO service-token-only `POST /v1/questions/operation`, body `{"operation":"acquire","arguments":{"event_seq":1,"revision":"0","request_id":"<stable-id>"}}`. Reply is `{"ok":true,"question":{...}}`, not a flat record. Existing owner ingress service token + current verified file-owned/0600 `dot-binding.json` derive the `dot` holder for the **bound bot account + owner private chat only**. Nonservice HTTP caller gets 403; rejection gets 409; no provider-send endpoint is exposed here. The private token is not a credential to issue to another actor, and no `owner`/account override from JSON is permitted.

The *raw* Telegram `77`, relay journal `botAccount:owner:77`, chat label, browser echo and `ROOM` are not this UserIO source ID. The existing `POST /v1/messages` returns `conversation_id` and `accepted` but **not** `event_seq`; resolve the actual persisted event through the existing `GET /v1/workspace/events?after=...&limit=...` (or existing authorized MCP workspace poll) and verify **all** source/account/conversation/message fields, direction incoming, current eligibility and sender not bot. No invented sequence, no claim based only on `postInbox.accepted`; if event is not present/eligible, fail closed. **Important:** the current workspace event preview does NOT expose `edited_at`. Resolve `revision` from the currently persisted exact source message (existing authenticated exact-message read) before claiming; use `"0"` only when that source is verified unedited. Never infer it from a stale preview, provider timestamp or model text. Do not disable policy for `telegram_bot` or edit/read-only accounts to force claims.

### Single original outgoing send fence / receipt

1. Claim before **either** `DotRelay.deliver` / `dot_send` (model input) or ExManager generation; if busy, paused, invalid binding, or UNKNOWN, do nothing and keep durable source.
2. Save a real draft/action through `userio.messenger.propose` with original **UserIO** `source_message_id`, same authenticated account/conversation, action `reply`, stable original `request_id`, and bounded payload. This creates the existing `messenger_actions` row but does **not** send.
3. `result_saved`: `result_ref="messenger:"+action.id` (not the raw provider message ID, not `request_id`, not ExManager card ID). A claim holder cannot invent this row; same saved source/user/account must match.
4. Only after exact human approval where required, invoke the existing `userio.messenger.approve` with `action_id`, immutable `expected_hash`, `confirm=true`, and **`question`** proof `{"event_seq":...,"revision":...,"epoch":...,"lease_token":...}`. **The `confirm=true` request flag alone is NOT evidence of human approval**: the ExManager consumer must retain its existing native `requires_user_confirmation` gate bound to the immutable action/hash and source, and the Mirror flow may send only under the existing approved owner policy. The backend rechecks live grants, source, CAS and journal and irrevocably records delivery `UNKNOWN` before provider I/O. It invokes existing transport once; no separate sender/queue or `_question_fence` callback from model JSON. No second call after unknown.
5. Reconcile by `userio.messenger.question.reconcile` with the **same original journal action** and a *new stable ID for each receipt-read attempt*: the state machine memoizes `request_id`, so reusing an old unknown reconciliation ID returns the old snapshot. `userio.messenger.get({action_id})` is read-only supporting evidence. `accepted` in original `messenger_actions` plus nonempty receipt produces `delivery_state="sent"` and `receipt_ref="messenger:"+action.id`; otherwise `unknown`. No inferred failed/sent on timeout; `complete` needs real result and defined receipt.
6. During unknown send, `handoff` remains pending `transferring`; do not automatically free/retry via `workspace.fail`. When receipt settles, reread current epoch/holder and explicitly `resume` before any new work. Completion-only adoption after expired TTL preserves original result/receipt and cannot resend.
7. A dot mirror reply **must not** call `client.sendMessage` directly for a question claimed under this shared fence. It must use the original approved UserIO `messenger_actions` operation/receipt. Existing `DotMirror` multi-part output currently creates multiple provider sends; this per-question contract permits only **one** original outgoing operation. Route bounded one-part response or explicitly fail closed on oversize rather than introducing multiple untracked chunks or a second fence. Ordinary non-question mirror behavior stays owned by Mirror.

## Source-review: dot human-approved Messenger action adapter is missing (2026-11-03)

**Not a new fence and not implemented by this documentation PR.** The current production source d5c1eb0 has an authenticated question-control endpoint and a separate Messenger send API, but **no trusted action-specific user approval bridge between them**. The Mirror successor correctly leaves `questionApproval` unconnected and holds correlated replies.

Evidence from exact current files:
- `http_api.py:390–412`: dot service-token-only `POST /v1/questions/operation` dispatches only `QuestionRuntime.dispatch`; `approve` is NOT an operation. A service principal here merely proves the existing dot binding and current lease, not human consent.
- `mcp_catalog.py`, `userio.messenger.approve` input: `action_id`, `expected_hash`, `confirm` and optional `question` proof; no server-verified `approval_ref`, user approval event, or actor attestation. `messenger.py::Messenger.approve` requires only `confirm is True`, immutable hash, and existing account/source and question lease guards before provider I/O. `question_runtime.py::_delivery_allowed` checks send capability and same original action; it does **not** establish that a human approved the exact payload.
- `messenger.py::Messenger._init_actions`: the original `messenger_actions` row records action hash/status/receipt but no durable `approved_by/approval_receipt/approved_at`. `userio.messenger.get` returns `{"ok":true,"action":{...}}`, **not** PR19's independently verified flat receipt projection.
- ExManager `airlock-agent/userio.go::userio_approve_send` is protected by its **native human confirmation gate**, but invokes `userio.draft.approve_send` on *drafts*, not `userio.messenger.approve` on `messenger_actions`. It cannot be reused as evidence of approval for a different action without a precise reviewed binding.

Therefore **a dot service token plus `confirm:true` is NOT an authorized callback**, even if a valid dot question lease exists. Do not supply a fake owner principal, borrow ExManager credentials, create a second provider send, or wire PR19's optional callback directly to the generic MCP approve method.

### Minimal missing interface (proposal for backend owner, not existing functionality)

1. **Trusted human admission:** reuse an existing *authenticated owner UI/native confirmation mechanism*, adding only action-specific acceptance for the exact persisted `messenger_actions` tuple: `user_id, account_ref, conversation_id, source_message_id, action_id, immutable expected_hash, exact outgoing body/hash, question_id, revision, epoch`. 2. **Single enforcement point:** before ANY provider execution of a *question-correlated* action, the already installed `Messenger.approve` / `QuestionRuntime.begin_original_send` path must require readback of that trusted action-specific approval AND current UserIO account grants/source/lease. Apply to generic MCP approve as well as a future internal callback so the latter cannot be bypassed. Keep the **same PR13 UNKNOWN-before-I/O send fence**. No `_question_fence` callback from stale PR12 or additional provider sender.
3. **Identity:** execute under the actual authenticated existing principal. A bound dot service principal may keep the `dot` lease only if the *separate human approval evidence* is verified at this same provider boundary; never classify it as owner. Alternatively hand off dot → manager and let a verified non-service owner principal perform the exact human-confirmed original approval, with dot polling the read-only receipt. 4. **Original receipt/readback:** use `messenger_actions` by original `action_id/request_id`, immutable source/body, and `userio.messenger.question.reconcile` with a new read-attempt ID when prior read was UNKNOWN. Return PR19's flat `{status:"accepted",question_delivery_state:"sent",account_ref,peer_id,source_provider_message_id,source_message_id,conversation_id,event_seq,revision,epoch,request_id,action_id,receipt_ref,provider_message_id,message_sha256}` ONLY after independent verification of the original accepted action and confirmed receipt. The current `userio.messenger.get` nested result is not this projection. No user/browser-supplied accepted flag, body hash or provider ID.
