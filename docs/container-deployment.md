# UserIO: frontend, backend и голос

Серверная установка состоит из **трёх контейнеров**. `backend` содержит API,
MCP, базу и фоновые процессы подключённых каналов. `frontend` раздаёт веб-интерфейс
и передаёт запросы авторизации/API в backend. `voice` содержит голосовой шлюз,
синтез речи и запись встреч. Голос можно перезапустить отдельно от сообщений.
Телефон, Asterisk, Matrix,
Notice Place и Agent Herder остаются внешними платформами.

Процессы каналов внутри backend сохраняют свои аккаунты, курсоры и журналы
отправок. Они запускаются обычными дочерними процессами; отдельные системные
службы для каждого канала больше не нужны. Проверка контейнера учитывает все
настроенные процессы, а не только HTTP-порт. При остановке завершаются только
его собственные процессы.

## Библиотека и готовое приложение

`userio_adapter_sdk` — библиотека Python без обязательных внешних зависимостей.
Её можно импортировать и использовать в своём приложении без веб-сервера,
Docker, systemd и Fast Agent. `Omnichannel` объединяет зарегистрированные
адаптеры; платформенный SDK подключается только для выбранного адаптера.
См. [Adapter SDK](adapter-sdk.md).

```python
from userio_adapter_sdk import Omnichannel

channels = Omnichannel()
# channels.register(ваш_адаптер, account_id="personal")
```

Готовый UserIO добавляет многопользовательский inbox, авторизацию, общую историю,
MCP, веб-интерфейс и постоянное получение сообщений. Эти функции требуют
запущенного приложения и сохранённого состояния. Три контейнера — способ
запустить это приложение; они не являются требованием для использования SDK.

## Перенос существующей установки

Канонический checkout остаётся на `main`. Не включайте чужие незавершённые
изменения в образ. `scripts/container_release.py context` читает опубликованные
Git-объекты и явно зафиксированный установленный dispatcher. Секреты,
SQLite-базы, `.env`, домашние профили и сессии в контекст сборки не попадают.

Перед переключением `prepare` сохраняет реальные настройки работающих
процессов в root-only `/etc/userio-containers`. Секреты не выводятся.
Данные продолжают использовать существующие `/var/lib` каталоги с теми же
правами и идентификаторами. Перед запуском контейнеров прежние клиенты
останавливаются; параллельных подключений старого и нового транспорта нет.
Архив и terminal-состояние прежнего удалённого RTC worker переносятся локально,
без повторного вступления во встречи.

Порядок операций: `prepare`, затем `prepare_voice` → ограниченная сборка опубликованных образов →
резервная копия → `cutover` → проверка настоящих подключений и веб-интерфейса.
Для конкретного сервера используется закрытый `compose.host.json` с путями
нужных существующих credentials; он не публикуется в репозитории.

```bash
sudo /opt/universal-userio/.venv/bin/python scripts/container_release.py prepare
python3 scripts/container_release.py context --output /var/tmp/userio-context.tar.gz
# Сборка backend/frontend из этого контекста выполняется с конечными лимитами.
sudo /opt/universal-userio/.venv/bin/python scripts/container_release.py cutover
docker compose -f compose.yaml -f /etc/userio-containers/compose.host.json ps
```

`prepare` и `cutover` не повторяют уже выполненный переход. После сбоя сначала
проверяется сохранённый результат. Откат запускает прежние службы на актуальной
базе, сохраняя новые сообщения и receipts:

```bash
sudo /opt/universal-userio/.venv/bin/python scripts/container_release.py rollback
```

Старую SQLite-копию нельзя автоматически накатывать поверх уже принятых
сообщений. Эти копии предназначены для отдельного восстановления данных.

## Ресурсы установленного проекта

На server-100 перед переносом было около24ГиБ доступной RAM и356ГиБ диска.
Текущие процессы UserIO использовали около0,5ГиБ на100 и0,09ГиБ для RTC на44;
сумма их прежних аварийных лимитов превышала4ГиБ. Новые лимиты заменяют эти
процессы, а не добавляются к ним на постоянной основе.

| Работа | RAM мягкая/жёсткая | CPU | Процессы | Swap | Временные файлы/логи |
|---|---|---|---|---|---|
| Backend | 2/4ГиБ | 4 | 512 | 256МиБ | tmp128МиБ, run16МиБ, логи30МиБ |
| Frontend | 64/128МиБ | 0,5 | 32 | 0 | tmp17МиБ, логи10МиБ |
| Сборка образа | 1ГиБ максимум | 2 | 256 | 0 | образы/контекст до6ГиБ |
| Профильные тесты | 512/768МиБ | 1 | 128 | 0 | tmp256МиБ |

Контейнеры находятся под существующим внешним `user-1000.slice`. Перед тяжёлой
работой проверяются свежая доступная память, живые нагрузки и резерв20ГиБ для
хоста. GPU не используется. Для сборки ожидается240с, аварийный предел2400с;
для профильной проверки8с/80с. Оценка времени не означает принудительную
остановку исправно работающего задания.

## Бюджет голосового контейнера

Измеренная постоянная нагрузка прежних голосовых процессов и RTC — менее0.4ГиБ;
их суммарные старые жёсткие пределы превышали8ГиБ, у аварийного синтезатора
предела не было. Новый voice: RAM2ГиБ резерв/6ГиБ предел,swap256МиБ,CPU4,
512процессов, временные файлы144МиБ,логи30МиБ. Backend сохраняет2/4ГиБ,
frontend64/128МиБ. Прежние экземпляры останавливаются до запуска новых;
это замена ресурсов, без удвоения провайдерских подключений. Сборка одна,
1ГиБ RAM,CPU2,pids256,swap0,кэш6ГиБ; свободная RAM хоста перед сборкой22ГиБ,
резерв20ГиБ. Для голоса ожидается480с/аварийный4800с.

Сохраняются разные установленные версии FastAgent:CLI0.10.43 и Python
служебного MCP0.10.42. Модель русской речи используется из прежнего кэша;
ключи, session/receipt state и записи хранятся вне образа. Неиспользуемый
старый Windows TTS tunnel18018 выводится из эксплуатации: действующие
настройки и исходник используют локальный синтез30802. Asterisk и физический
телефон остаются внешней общей инфраструктурой. Их нельзя включать в перезапуск UserIO.
