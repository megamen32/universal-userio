# Как устроен User.io

## Основной поток

```text
Аккаунт провайдера ↔ адаптер / отдельный коннектор
                           ↕
                        User.io
                  сообщения и контекст
                  пользователи и права
                  черновики и подтверждения
                           ↕
                    MCP / HTTP API
                           ↕
                        ИИ-клиент
```

UserIO — универсальный шлюз коммуникаций: сообщения, чаты, переписка, файлы,
звонки и встречи через подключённые аккаунты. Он сохраняет происхождение
событий, историю, курсоры, права и результаты операций. Коннектор выполняет
операции конкретного провайдера.

Для уведомлений и вопросов агентов есть один прикладной вход:

```text
Агент → Notice Place (API/MCP: вопрос, расписание, эскалация)
      → UserIO (аккаунт, права, транспорт, результат доставки)
          ├─ Telegram: сообщения и поддерживаемые голосовые звонки
          ├─ Matrix: комнаты и поддерживаемые MatrixRTC-звонки
          ├─ Телемост: чаты Яндекса и поддерживаемые операции со встречами
          └─ Сотовая связь: настроенный SIP / GSM2SIP на телефоне
```

Обычная переписка и чтение истории по-прежнему доступны через UserIO API/MCP.
Наличие низкоуровневого инструмента звонка не разрешает агенту обходить
настройки контакта с оператором в Notice Place.

UserIO Voice — внутреннее исполнение голосовых операций. AgentCall — название
используемого голосового/ИИ-моста, не ещё один самостоятельный продукт.
Asterisk и GSM2SIP относятся к сотовому маршруту; Telegram, Matrix и Телемост
не обязаны проходить через них. Не следует удалять процессы только ради более
простой схемы: сначала нужны проверенный маршрут, отсутствие активных звонков
и способ отката. [Нормативный контракт архитектуры](../COMMUNICATIONS-ARCHITECTURE.md).

## Четыре идентификатора

| Понятие | Зачем нужно |
| --- | --- |
| Пользователь User.io | Определяет область данных и прав |
| Аккаунт канала | Определяет, через какую учётную запись пришло сообщение |
| Диалог | Объединяет историю конкретной переписки |
| Исходное сообщение | Позволяет распознать повторную доставку и вернуться к источнику |

Не используйте отображаемое имя вместо устойчивого ключа аккаунта или Telegram peer ID. Одинаковые названия чатов не означают, что это один разговор.

## Входящее событие и исходящий ответ

Приём сообщения сохраняет его и обновляет состояние синхронизации. Генерация ответа создаёт черновик. Отправка проходит отдельную проверку полномочий, политики и выбранного исходящего маршрута.

Для правил с `auto_send` есть отдельный разрешённый путь автоматической доставки. Его не следует включать как побочный эффект подключения канала.

## Роли в экосистеме

**UserIO:** универсальный транспорт сообщений, звонков и встреч; аккаунты, права, история и проверяемые результаты операций.

**GPTAdmin:** приём события и вызов заданного инструмента по конфигурации маршрута.

**Agent Herder:** управление агентными сессиями, в том числе создание, возобновление и продолжение именованной сессии.

**Native Fast Agent и модель:** обычная оценка, резюме и черновики внутри runtime. Отдельный агентный клиент обслуживает подробный анализ и настроенные внешние маршруты.

**Notice Place:** уведомления, вопросы человеку, расписание контактов, инциденты
и эскалации. Публичные API/MCP принимают агентский запрос, а передачу выполняет
UserIO. Подтверждённый ответ связывается с исходным вопросом и сессией.
Обычные ответы собеседникам не подменяются системными уведомлениями.

Статусы «запрос принят», «звонок начат», «человек ответил» и «решение подтверждено»
не равнозначны. При неизвестной доставке проверяется прежняя квитанция, а не
запускается повторный звонок.

## Контекст не равен всему архиву

Параметры User.io ограничивают недавнюю историю и объём контекста для разбора. Дополнительное чтение и кэш резюме управляются отдельно. Передача в ИИ должна соответствовать задаче и разрешениям пользователя.
