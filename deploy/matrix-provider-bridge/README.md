# MAX ↔ Matrix и VK ↔ Matrix

Стандартный Matrix Application Service для личных аккаунтов, уже подключённых к
UserIO. Провайдерные сессии, чтение и подтверждённая отправка остаются у UserIO.
Мост создаёт отдельные пространства MAX/VK, комнаты личных диалогов и групп,
Matrix-пользователей собеседников и события `m.bridge`. Каналы исключены.

Двусторонний текст и изменения своих текстовых сообщений проходят через
существующие HTTP API UserIO. Изображения и файлы MAX/VK до 2 МиБ передаются в обе стороны через существующие
нативные клиенты UserIO. MAX-изображение при отправке использует файловый
транспорт. Реакции, звонки, перенос удаления и нативное дерево ответов этим
выпуском не поддерживаются. Matrix reply отправляет
написанный текст без служебной цитаты. История при создании комнаты — последние
10 сообщений; последующие проходы читают до 200 сохранённых сообщений.

Выход из комнаты Matrix останавливает её локальную синхронизацию. Мост не
вызывает выход из MAX/VK, удаление удалённой переписки или контакта. Возврат
в ту же комнату возобновляет её. Сквозное шифрование пока не поддерживается:
при его включении комната приостанавливается.

## Развёртывание

Владельцы исходников: этот каталог canonical UserIO на server-100.
Установленный Python: `/opt/userio-matrix-bridge/bridge.py`.
Конфигурация/состояние: `/var/lib/userio-matrix-bridge/`; режим 0700/0600.
Matrix runtime: canonical server-88 `/home/roomhacker/matrix-synapse`.
Регистрационный файл (с секретами) находится в runtime `data/`; его путь
добавляется к `app_service_config_files` перед единственным перезапуском Synapse.
Топология: [канонический runbook](https://github.com/megamen32/ServersAdministartion/blob/main/docs/projects/MATRIX.md).

Используются отдельный personal token владельца UserIO и его существующий
Matrix-токен. Токен UserIO создан обычным PersonalTokens API: сервисный ingress
токен не выдаётся за человеческую отправку. Config фиксирует конкретные
аккаунты и Matrix-владельца. Чужие Matrix-сообщения не отправляются провайдерам.

AS transactions сначала сохраняются в SQLite, затем подтверждаются HTTP 200.
Повтор transaction/event ID не дублирует отправку. UserIO получает стабильный
request_id из Matrix event ID и сохраняет исход доставки. Неясная отправка
остаётся failed с уведомлением; автоматического повторного внешнего действия нет.
Matrix → provider отправка, provider echo и Matrix event связываются в пределах
конкретной комнаты и аккаунта. Старые комнаты восстанавливаются по постоянному
зарезервированному alias, а не создаются снова после перезапуска.

## Бюджет и проверка

На server-100 перед началом проверены 43 ГиБ доступной RAM и 237 ГиБ свободного
диска, текущий UserIO ограничен 384/512 МиБ и CPU1/Tasks64. Новый мост имеет
собственный конечный бюджет: RAM96/192 МиБ, swap0, CPU0.5, Tasks32, IOWeight25,
128 дескрипторов, один рабочий цикл без пула провайдерных сессий. Нет GPU.
SQLite ограничена 512 МиБ, journal target8 МиБ; файлы вложений до 2 МиБ
обрабатываются последовательно в памяти. Журнал ограничен native rate limit.
Тест не запускает браузеры, серверы или дополнительные провайдерные клиенты.

`python3 -m unittest -v test_bridge` — fast unit, expected2s/max30s:
изоляция аккаунта и автора, точная доставка, повторы/неясная отправка,
Matrix leave/rejoin, edits и отсутствие echo-дублей. Первый прогон:15PASS/1.30s.
Focused integration — expected30s/max180s: реальный входящий источник →
Matrix; сообщение человека из Matrix → переписка с собой в VK/MAX;
повтор transaction и рестарт не дают второй отправки. Не требует чужого адресата.
Slow nightly отсутствует: полный сторонний messenger suite здесь не запускается.

Остановка: `sudo systemctl stop userio-matrix-bridge`. Сохранить state/config,
удаление комнат и provider-logout не делать. Регистрацию при обычной остановке
не удалять: Synapse сохранит недоставленные transactions для возобновления.

## Telegram-форумы

telegram_forums.py использует существующие mautrix-регистрации и известные
проверенные ID рабочих форумов. Каталог с личными названиями/ID хранится только
в защищённом runtime и ignored .tmp, не в Git. Топик1 соответствует General
без числового suffix в mautrix portal ID; остальные топики — отдельные дочерние
комнаты пространства форума. Родители явно связаны с личным пространством Telegram.

Существующие темы из native Telegram каталога создаются штатной create-portal
командой. Следующие новые topic stubs в тех же форумах допускаются фильтром и
создаются при bounded проходе. Ни команды remote delete-chat, ни выход из
Telegram не вызываются. Каналы/обсуждения по-прежнему исключены.

На server-88 oneshot unit: RAM32/64MiB,swap0,CPU0.25,Tasks16,IO10,wall60s.
Каталог до256тем; SQLite-снимок из существующего файла, без нового клиента,
GPU, браузера и нового checkout. Таймер с периодом1мин принадлежит этому
мосту и восстанавливает навигацию; повтор команды не создаёт второй portal.


## Предупреждение о владельце устройства Telegram

Проверено на живом mautrix-telegram 2026-10-14: encryption allow/default/self_sign
включены, msc4190 включён, appservice encryption выключен. Crypto account
моста использует одну сессию бота. Сообщение клиента «отправитель события и
владелец устройства не совпадают» соответствует известному ограничению
mautrix: сообщения пользователей Telegram шифруются устройством бота.

Это предупреждение не устранено. self_sign уже включён и не устраняет
несовпадение отправителя. Шифрование и проверки клиента не отключались.
Блокер: поддержка делегирования криптографии одновременно мостом и клиентом;
[MSC4350](https://github.com/matrix-org/matrix-spec-proposals/pull/4350)
остаётся открытым предложением. Следующий шаг — проверить совместимую
реализацию после её появления, затем принять реальное сообщение в клиенте
без этой отметки. Переход на комнаты без шифрования требует отдельного
решения владельца, не является автоматическим исправлением.

Источник: [официальный FAQ mautrix](https://docs.mau.fi/bridges/general/troubleshooting.html#why-are-messages-showing-up-as-encrypted-by-a-deleted-session).


## Перенос Telegram-комнат без шифрования

telegram_plaintext_migration.py — разовая возобновляемая миграция, явно
разрешённая владельцем 2026-10-14. Исходники в этом каталоге; выполнение только
в canonical Matrix runtime на server-88. Новый checkout не создаётся.
Стадии inventory/create/cutover/finish/verify используют защищённый manifest.
Выбираются только уже зашифрованные Telegram portals, в которых владелец
состоит. Пространства и обычные Matrix-чаты не перепривязываются.

Перед cutover создаются отдельные комнаты без m.room.encryption,
с теми же bridge metadata, именами, разрешениями и Telegram ghosts.
Существующие пространства форумов сохраняют ID и получают новые дочерние
комнаты. Короткая остановка только mautrix-telegram нужна для атомарной
перепривязки portal rows и удаления старых event mappings из bridge SQLite.
Это не удаляет историю Synapse: старые Matrix-комнаты, участники,
зашифрованные события и ключи сохраняются. Старые комнаты получают
ссылку на продолжение, права только для чтения и отдельное дерево архива.

encryption.default=false применяется только к mautrix-telegram. allow=true
сохраняет поддержку зашифрованной management-комнаты; глобальные настройки
Synapse, MAS, клиентские устройства и обычные Matrix-чаты не меняются.
Backfill остаётся выключенным. Скрипт не вызывает Telegram API, remote leave,
logout, remote edit/delete или send.

Бюджет server-88: RAM256/384MiB,swap0,CPU0.5,Tasks32,IO25;
один последовательный проход, не более256portals,512ghosts на комнату,
ответ Matrix до4MiB, manifest до32MiB, два SQLite backup до256MiB каждый,
всего временное состояние до600MiB; без GPU/браузеров. Каждая стадия
oneshot с wall600s и checkpoint; после timeout повторяется та же стадия,
новая комната восстанавливается по маркеру в initial_state.
Регистрация Telegram AS не разрешает создавать room aliases; namespaces
и регистрация Synapse не расширяются ради миграции.
Измеренная свободная память перед миграцией — 98GiB; штатный мост ограничен
512MiB/swap0/CPU1/Tasks128, его бюджет не повышается.

Fast unit migration tests: expected2s/max30s; проверяют изоляцию portal keys,
атомарный отказ при чужой перепривязке, сохранение чужих mappings,
отсутствие encryption в создаваемой комнате и восстановление после
потерянного ответа createRoom по маркеру состояния.
Focused integration: отдельная партия проверки expected30s/max180s;
настоящие Matrix state/membership/portal rows, обычные чаты,
дерево форумов и архива. Последний canary после всех рестартов:
Matrix-сообщение только в Telegram Saved Messages и подтверждённое
plaintext-событие в новой комнате. Медленная nightly не нужна.

Обновление AST-графа после исходников: один bounded процесс, RAM256/512MiB,
swap0,CPU1,Tasks32,wall120s,temporary output до100MiB,без GPU/LLM. GRAPHIFY_MAX_WORKERS=2,
OMP_NUM_THREADS=1,OPENBLAS_NUM_THREADS=1: host cpu_count не используется
как разрешение размножить процессы за конечный TasksMax. Первый AST проход
без worker override достиг wall120s; повтор только с уменьшенной параллельностью.
